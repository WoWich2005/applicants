\section{Тестирование приложения}

Функциональное тестирование является неотъемлемой частью процесса проверки качества программного обеспечения.
Его основная задача~--~удостовериться, что реализованный функционал соответствует установленным требованиям и корректно работает при типичных сценариях взаимодействия пользователя с системой.
Данный вид тестирования помогает оценить, насколько эффективно информационная система решает поставленные перед ней задачи в условиях, максимально приближенных к реальному использованию.
В ходе проверки охватываются все ключевые функции приложения с целью подтверждения их соответствия предполагаемому поведению.

Различают два основных метода функционального тестирования:
\begin{itemize}
    \item тестирование <<чёрного ящика>> (Black Box)~--~проводится без изучения внутренней структуры приложения, основываясь исключительно на входных и выходных данных;
    \item тестирование <<белого ящика>> (White Box)~--~предполагает анализ кода, логики обработки и внутренних механизмов системы.
\end{itemize}

В рамках реализации проекта применялся метод чёрного ящика.
Серверная часть приложения проверялась через интерактивный интерфейс Swagger~UI, генерируемый средствами библиотеки Swashbuckle.AspNetCore по спецификации OpenAPI: эндпоинты REST API вызывались с подготовленными входными данными, после чего сверялись фактические HTTP-статусы и тела ответов с ожидаемыми.
Пользовательский интерфейс проверялся вручную в браузере Google~Chrome последовательным выполнением основных сценариев работы оператора приёмной комиссии.

Тестирование охватило основные бизнес-процессы: аутентификацию пользователей, разграничение прав доступа по ролям, постраничное получение списков сущностей, создание и редактирование структуры (факультеты, кафедры, специальности, конкурсные списки, основания зачисления), ввод данных абитуриентов и их оценок, автоматический пересчёт результатов отбора, валидацию данных оператором с правом аудита, двухступенчатое удаление абитуриентов, выгрузку результатов отбора в~\code{xlsx}, локализацию сообщений об ошибках.
Тестирование выполнялось разработчиком вручную по заранее подготовленным сценариям.

По результатам функционального тестирования установлено, что разработанное приложение корректно реализует все сформулированные функциональные требования.
Все запланированные тестовые случаи (20~шт.) пройдены успешно.
Обнаруженные в процессе разработки ошибки были устранены до этапа итогового тестирования.

Помимо функционального тестирования, для проверки корректности реализованного алгоритма отбора было проведено валидационное тестирование на реальных данных приёмной комиссии БНТУ за 2024~год.
В систему были загружены сведения об абитуриентах, поданных ими заявлениях, выбранных специальностях и полученных баллах вступительных испытаний, после чего был запущен полный пересчёт результатов отбора.
Полученные системой результаты сопоставлялись с фактическими итогами приёмной кампании 2024~года: для каждой специальности проверялось совпадение состава зачисленных абитуриентов, а также совпадение проходных баллов по каждому конкурсному списку.
По итогам сравнения зафиксировано полное совпадение результатов~--~как по персональному составу зачисленных, так и по значениям проходных баллов по всем конкурсным спискам.
Это подтверждает, что реализованный алгоритм отбора соответствует действующим правилам приёма в БНТУ и применим для эксплуатации в реальной приёмной кампании.
